# vegasroom

Vegasroom is a small CLI for running AI coding agent harnesses inside ephemeral, rootless Docker containers. It gives each agent a predictable room to work in: a mounted workspace at `/workspace`, persistent harness state, optional SSH/Git access, and a disposable container that is removed when the session ends.

Supported harnesses:

| Harness | Command | Agent |
| --- | --- | --- |
| Pi (default) | `vr pi` / `vr` | `@earendil-works/pi-coding-agent` |
| Claude Code | `vr claude` | `@anthropic-ai/claude-code` |

Vegasroom is a convenience wrapper, not a hardened sandbox.

## Requirements

- Linux
- Docker with Compose v2 (`docker compose`)
- A Docker context named `rootless`
- Rust and Cargo to build/install Vegasroom from this repository

Check the Docker context before installing:

```bash
docker context ls
docker --context rootless info
```

## Install

From the repository checkout:

```bash
cargo install --path .
```

This installs the `vr` command.

Initialize Vegasroom state and build the harness images:

```bash
vr init --build
```

`vr init --build` creates `~/.vegasroom`, writes the managed Docker Compose runtime (one service per harness), and builds the images from the Dockerfiles bundled in the `vr` binary: first the shared base image `vegasroom/base:latest`, then `vegasroom/pi:latest` and `vegasroom/claude:latest` on top of it. See [Images and the environment profile](#images-and-the-environment-profile).

Plain `vr init` (without `--build`) writes state and runtime files only; use it after reinstalling `vr` when the images already exist.

Verify the setup:

```bash
vr doctor
```

## Update the harnesses

### Pi

From this checkout **on the Docker host**, close running Pi sessions and run:

```bash
./scripts/update-harness.sh          # latest published Pi release
./scripts/update-harness.sh 0.85.1   # or an exact version
```

The script requires npm and Perl in addition to the installation requirements. It:

1. Resolves the version through npm and pins `harness/pi/Dockerfile`.
2. Runs `scripts/check.sh` (script tests, Rust formatting, Clippy, and tests).
3. Reinstalls `vr` from this checkout. The harness Dockerfiles are embedded in the binary (and the Compose file is generated by it), so rebuilding with an old `vr` would use the old pin.
4. Runs the new `vr init --build`, rebuilding the shared base image and the harness images with your Docker context and network settings. The base comes from the build cache unless your environment profile changed, so only the Pi layer is rebuilt.
5. Installs the same exact Pi version in the persistent npm prefix, which takes precedence over the image's Pi install. Checks both versions.
6. Runs `pi update --extensions` for all global Pi-managed packages, lists them, then runs `vr doctor`.

Package updates include packaged extensions, skills, prompts, and themes. Explicit npm versions and Git refs are retained, not advanced to newer versions. Local paths, manually copied extensions, and project-local packages are not upgraded. Register shared extensions with `pi install npm:...` or `pi install git:...` to include them in this update flow. Package updates can execute third-party install scripts; only update packages you trust.

The script installs `vr` into `${CARGO_INSTALL_ROOT:-${CARGO_HOME:-$HOME/.cargo}}/bin` and uses that exact binary, not another `vr` on `PATH`. Keep that directory first on your host `PATH` for subsequent launches.

Failures stop the script immediately. Completed file, image, and package changes are not rolled back. Back up `~/.vegasroom` first if you need rollback, fix any reported error, then rerun. Review and commit the Dockerfile pin after a successful update. Start a new Pi session to load the updated packages.

### Claude Code

Claude Code is pinned by `ARG CLAUDE_CODE_VERSION` in `harness/claude/Dockerfile`, and in-room auto-updates are disabled (`DISABLE_AUTOUPDATER=1`), so rebuilding the image is the only upgrade path. Until `vr update` exists, update it manually:

```bash
npm view @anthropic-ai/claude-code dist-tags   # pick a version, e.g. the `stable` tag
# edit ARG CLAUDE_CODE_VERSION=... in harness/claude/Dockerfile
bash scripts/check.sh
cargo install --path .
vr init --build
vr doctor
```

## Use

Launch Pi in the default managed workspace:

```bash
vr
```

Launch Pi in the current directory:

```bash
vr pi .
```

Launch Pi in a named managed workspace under `~/.vegasroom/workspace`:

```bash
vr pi my-project
```

Pass arguments through to Pi:

```bash
vr --session abc123
vr pi . --session abc123
vr -- ask Pi a question
```

Launch Claude Code in the current directory, or pass arguments through to it:

```bash
vr claude .
vr claude my-project
vr claude . --resume
vr claude . -- --help
```

Top-level shortcuts (`vr`, `vr --flag`, `vr -- args`) always launch the default harness (Pi); use `vr claude ...` explicitly for Claude Code.

Open a shell in the same container environment:

```bash
vr shell .
```

Run a command in that environment without a pseudo-TTY (returns its exit status):

```bash
vr shell . -- sh -c 'node --version'
```

Configure Vegasroom interactively:

```bash
vr config
```

Use command help for the exact current command surface:

```bash
vr --help
vr pi --help
vr claude --help
vr shell --help
```

## Claude Code

### Authentication

Either works; Vegasroom never writes your key into its files:

- **Log in through the browser inside the room.** The first `vr claude` launch runs Claude Code's onboarding: pick a theme, then a login method (Claude subscription or Anthropic Console). The room cannot open a browser, so Claude Code shows the sign-in URL instead:
  1. Press `c` to copy the URL. This uses the OSC 52 terminal clipboard, which works from inside the container in kitty, WezTerm, Alacritty, foot, iTerm2, Windows Terminal, and tmux with `set-clipboard on`. In terminals without OSC 52 (e.g. GNOME Terminal), select the URL instead and remove any line breaks.
  2. Open it in your host browser and approve.
  3. Paste the code the page shows back at the `Paste code here` prompt.

  The callback goes through `platform.claude.com`, not `localhost`, so this works with both `host` and `bridge` networking. Credentials are saved in `~/.vegasroom/harness/claude/config/.credentials.json` and reused by every later Claude Code room; onboarding is only marked complete after a successful login, so an abandoned first run starts over next time. Use `/login` later to switch accounts.
- **Use an environment variable.** If `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) is set in the shell where you run `vr`, it is forwarded into the room. If you keep an API key exported for other tools, Claude Code will see it and may ask whether to use it instead of your `/login` account.

`vr doctor` reports a Claude Code login as ready when either is present.

### State

Claude Code runs with `CLAUDE_CONFIG_DIR=/home/agent/.claude`, bind-mounted from `~/.vegasroom/harness/claude/config`. Settings, login credentials, sessions and history, user-level `CLAUDE.md`, skills, agents, plugins, and user-scoped MCP configuration (`.claude.json` is written inside this directory) all persist there. Project `CLAUDE.md` files live in your workspace as usual. Your host `~/.claude` is not mounted, and Vegasroom refuses to mount it (or any harness's credential directory) as a workspace.

### Permissions

The room runs as container root, which rootless Docker maps to your unprivileged host user. Claude Code refuses `--dangerously-skip-permissions` when it sees uid 0, so that flag is not usable in the room; normal permission prompts work as usual.

## How it works

- `vr` defaults to `vr pi`.
- Each harness or shell launch starts a fresh container through Docker Compose and removes it after exit. `vr shell` uses the Pi image.
- The selected host workspace is mounted at `/workspace`.
- Per-harness state persists under `~/.vegasroom/harness/<id>/`: Pi configuration, extensions, skills, sessions, and npm-global installs; Claude Code's config directory. SSH state, caches, and the Cargo home are shared by all harnesses.
- Every harness image is built on one shared base image (Debian bookworm, Node 24, Git, OpenSSH, ripgrep, fd, build tools, plus your environment profile); see below.
- Per-harness settings (`image`, `command`, `network`, `build_network`, `read_only_workspace`, `read_only_rootfs`) live under `harness.pi` and `harness.claude` in `~/.vegasroom/config.yaml`. `vr config` currently edits the Pi settings; edit the YAML directly for Claude Code.
- Host SSH agent forwarding is used when available; managed SSH can be configured with `vr config`.
- `compose.yaml` in this repository is a reference copy of the generated `~/.vegasroom/runtime/compose.yaml`.

## Images and the environment profile

```text
node:24-bookworm-slim
  └─ vegasroom/base:latest     foundation + your environment profile (built once)
       ├─ vegasroom/pi:latest       + Pi agent
       └─ vegasroom/claude:latest   + Claude Code agent
```

- **Environment profile.** `environment:` in `~/.vegasroom/config.yaml` (or `vr config`) selects extra apt packages and the Rust, Python, Go, and TypeScript toolchains. It is one shared profile: it is installed once, into the base image, and every harness sees the same tools.
- **Base image.** `environment.base_image` (default `vegasroom/base:latest`) names it. Its Dockerfile is the bundled foundation followed by sections generated from your profile; the copy used for the last build is at `~/.vegasroom/runtime/harness/base/Dockerfile`.
- **Harness images** contain only their agent, so bumping an agent version rebuilds a thin layer, not the toolchains. `harness.<id>.image` is the tag `vr init --build` gives that image; it must be built by `vr` (`FROM` the base) to include your profile.
- **Rebuild after changing the profile** with `vr init --build`. Until then, `vr pi`/`vr claude` and `vr doctor` warn that the base is out of date (the base records a fingerprint of the profile it was built from), or that a harness image was built on an older base. Launches still go ahead.
- **Unused images.** After a build, and in `vr doctor`, Vegasroom lists local tags in its image repositories that your config no longer uses, with a ready `docker image rm` command. It never deletes images itself.

### Upgrading from per-harness `-env` images

Versions before the shared base built an extra `<image>-env` image per harness when a profile was configured (for example `vegasroom/pi:latest-env`). They are no longer used. Run `vr init --build` once to build the base and the new harness images, check `vr doctor`, then remove the old tags with the command it prints.

## Workspaces

Workspace arguments are resolved as follows:

```text
no workspace     ~/.vegasroom/workspace
.                current host directory
name             ~/.vegasroom/workspace/name
relative/path    relative to current host directory
~/path           expanded against host home
/absolute/path   used directly if it exists
```

Examples:

```bash
vr pi
vr pi .
vr claude ~/code/my-project
vr claude /home/me/code/my-project
```
